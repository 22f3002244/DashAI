ABSTRACT
--------------------------------------------------------------------------------

Dash AI is an AI-powered analytics and dashboard platform that transforms raw
machine data into interactive, personalized, and insight-rich visual dashboards
without requiring any manual configuration from the user. In its current Phase 1
implementation, the platform is purpose-built for IoT telemetry data sourced
from ThingsBoard — an open-source IoT data management platform — as per the
requirements of the commissioning organisation. However, the architectural
philosophy and pipeline design of Dash AI are intentionally data-source-agnostic.
The system is conceived as a general-purpose "any data, any source → AI
dashboard" platform. Future phases envision support for local file uploads
(CSV, Excel, JSON, SQLite), direct REST API integrations with cloud IoT
platforms (AWS IoT, Azure IoT Hub, Google Cloud IoT Core), time-series
databases (InfluxDB, TimescaleDB), third-party analytics services (Grafana,
DataDog, New Relic), and industrial SCADA/MES systems. The abstraction
layer introduced by the 4-agent pipeline ensures that a change in data source
requires only replacing Agent 1 (the DataFetcher), while the analytical,
visualisation, and presentation layers remain entirely unchanged.

1. INTRODUCTION & MOTIVATION
================================================================================

The exponential growth of connected devices, cloud services, and data-generating
systems has made "data" ubiquitous. Every organisation — from a smart-factory
running 10,000 sensors to a researcher analysing a local CSV export — generates
data that contains insights waiting to be discovered. Yet the gap between raw
data and actionable insight remains enormous.

Traditional BI tools (Tableau, Power BI, Grafana, Metabase) require significant
manual effort: selecting chart types, choosing aggregations, configuring axes,
creating calculated fields, and arranging layouts. Even for a skilled analyst,
building a useful dashboard from a new dataset takes hours. For non-technical
users, it is often impossible.

Dash AI addresses this problem through a principle it calls Zero-Config
Intelligence: a user supplies only three things — (1) a data source, (2)
credentials to access it, and (3) the time window of interest. The system
handles everything else automatically, delivering a complete, insightful,
and interactive dashboard in under 60 seconds.

The motivation for the platform comes from three observations:

  1. DATA SOURCE DIVERSITY: Modern organisations use dozens of data systems.
     A single platform that can ingest data from any source — IoT platforms,
     cloud databases, local files, or third-party APIs — provides dramatically
     more value than one locked to a single vendor.

  2. LLM CAPABILITY: The emergence of powerful instruction-following language
     models (GPT-4, Mixtral, LLaMA) makes it possible for software to reason
     about data the way a skilled analyst would: understanding what a "temperature"
     sensor should look like, what chart is best for boolean on/off states, and
     what correlations between sensors are worth noting.

  3. REAL-TIME EXPECTATIONS: Modern users expect dashboards to be live. The
     ability to stream telemetry updates to an already-rendered dashboard via
     WebSockets — without a page refresh — is now a baseline expectation for
     any monitoring application.

Phase 1 of Dash AI implements this vision for ThingsBoard-hosted IoT data,
as required by the commissioning organisation. The architecture is deliberately
designed to make Phase 2 onwards (described in Section 4) a matter of adding
data-source adapters, not redesigning the system.

2.3  AGENT PIPELINE ARCHITECTURE
-------------------------------------------------------

The pipeline follows an Chain-of-Responsibility / Blackboard pattern.
A single shared state object (AgentState TypedDict) is passed sequentially
through all four agents. Each agent reads from the state, enriches it, and
returns the modified state. No inter-agent communication channels are needed.

  INPUT
  ┌─────────────────────────────────────────────────────────────┐
  │  tb_host · tb_token · device_id · time_range                │
  └─────────────────────────────────────────────────────────────┘
        │
        ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  AGENT 1: DataFetcher                                        │
  │  ─────────────────────────────────────────────────────────  │
  │  Reads:  tb_host, tb_token, device_id, time_range           │
  │  Writes: raw_data { telemetry, attributes, device metadata } │
  │  Status: running → done | error                              │
  └─────────────────────────────────────────────────────────────┘
        │  raw_data
        ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  AGENT 2: DataCleaner                                        │
  │  ─────────────────────────────────────────────────────────  │
  │  Reads:  raw_data                                            │
  │  Writes: cleaned_data { numeric, boolean, string, stats }   │
  │          patterns [ trend, anomaly, constant, categorical,  │
  │                     correlation (AI-assisted if configured) ]│
  │  Status: running → done | error | skipped                    │
  └─────────────────────────────────────────────────────────────┘
        │  cleaned_data + patterns
        ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  AGENT 3: VizRecommender                                     │
  │  ─────────────────────────────────────────────────────────  │
  │  Reads:  cleaned_data, patterns, raw_data (device context)  │
  │  Writes: viz_recommendations [ { id, title, type, keys,     │
  │                                   description, priority } ] │
  │  Calls:  Groq Mixtral-8x7b or _fallback_viz()               │
  │  Status: running → done (never errors, fallback used)        │
  └─────────────────────────────────────────────────────────────┘
        │  viz_recommendations
        ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  AGENT 4: DashboardBuilder                                   │
  │  ─────────────────────────────────────────────────────────  │
  │  Reads:  cleaned_data, viz_recommendations, patterns         │
  │  Writes: dashboard_data { kpi_cards, bool_cards,            │
  │                            chart_blocks (Chart.js configs), │
  │                            attr_table, patterns, summary }  │
  │  Status: running → done | error                              │
  └─────────────────────────────────────────────────────────────┘
        │  dashboard_data
        ▼
  OUTPUT: Complete, renderable dashboard JSON


2.4  DATA FLOW ARCHITECTURE
-------------------------------------------------------

The following describes the high-level data flow for a standard "Generate
Dashboard" request, from the moment the user clicks the button to when charts
appear on screen:

  [Browser] POST /run
        │ { tb_host, tb_token, device_id, time_range }
        ▼
  [Flask /run endpoint]
        │ calls pipeline.run_pipeline()
        │
        ├── [DB] INSERT session record
        │
        ├── [DataFetcher]
        │       GET {tb_host}/api/device/{id}              → device name/type
        │       GET {tb_host}/api/.../keys/timeseries      → available keys
        │       GET {tb_host}/api/.../values/timeseries    → historical data
        │       GET {tb_host}/api/.../values/attributes    → device settings
        │       [DB] INSERT agent_log entries (per step)
        │
        ├── [DataCleaner]
        │       Pure Python statistics computation
        │       POST api.groq.com (optional, llama-3.1-8b) → correlations
        │       [DB] INSERT agent_log entries
        │
        ├── [VizRecommender]
        │       POST api.groq.com (mixtral-8x7b-32768)    → chart selection
        │       [fallback if Groq unavailable]
        │       [DB] INSERT agent_log entries
        │
        └── [DashboardBuilder]
                Pure Python Chart.js config construction
                [DB] INSERT agent_log entries
        │
  [Flask /run] returns dashboard_data JSON
        │
  [Browser]
        │
        ├── GET /logs/{session_id}   → populate activity log sidebar
        ├── renderDashboard(d)       → build HTML + instantiate Chart.js
        └── socket.emit('subscribe_telemetry') → connect WebSocket feed

  Then every 3 seconds:
  [APScheduler background thread]
        └── GET {tb_host}/api/.../values/timeseries (latest values)
               → socketio.emit('telemetry_update', data, to=sid)
                      → [Browser] handleLiveTelemetry()
                             → chart.update('none') + appendLog()

3. CURRENT IMPLEMENTATION: THINGSBOARD INTEGRATION (PHASE 1)
================================================================================

In Phase 1, Dash AI is implemented as a dedicated analytics companion for
ThingsBoard — the leading open-source IoT device management and data collection
platform. This decision was driven by the commissioning organisation's existing
ThingsBoard infrastructure and the requirement to deliver a production-ready
product quickly.

ThingsBoard provides a REST API that Dash AI uses exclusively via the
requests library. The integration supports:

  Authentication modes:
    - Email + Password: POST /api/auth/login → JWT token
    - Direct JWT paste: GET /api/auth/user validation
    - SSL fallback: requests.exceptions.SSLError → retry with verify=False
      (for self-hosted servers without valid certificates)

  ThingsBoard deployment types supported:
    - ThingsBoard Cloud      (thingsboard.cloud)
    - ThingsBoard Demo       (demo.thingsboard.io — public demo)
    - Self-hosted Community  (user-provided URL)
    - Professional Edition   (PE/Edge, user-provided URL)

  Account tier compatibility:
    - Tenant administrators: /api/tenant/devices
    - Customer users: /api/customer/{customerId}/devices

  Data retrieval:
    - Up to 20 telemetry keys per device (API batch limit)
    - Up to 1,000 data points per key per request
    - Time-range bounded (startTs/endTs in Unix milliseconds)
    - Aggregation mode: NONE (raw values, no server-side averaging)
    - Attribute scopes: client, server, shared (all three fetched)

  Multi-device mode:
    - device_id field accepts comma-separated UUIDs
    - Results merged with "DeviceName - " key prefix
    - Combined summary: device names joined, types de-duplicated

  Live telemetry:
    - /api/plugins/telemetry/DEVICE/{id}/values/timeseries (latest only)
    - Polled every 3 seconds via APScheduler background thread
    - Delivered to browser via Socket.IO WebSocket

The ThingsBoard-specific code is entirely confined to:
  agents/data_fetcher.py   (data acquisition)
  routes.py :: api_login() (ThingsBoard JWT authentication)
  routes.py :: api_devices() (ThingsBoard device listing)
  routes.py :: fetch_live_telemetry() (ThingsBoard live poll)

Everything else in the system (DataCleaner, VizRecommender, DashboardBuilder,
the entire frontend, the database layer, the auth system) is agnostic to the
data source.

4. BROADER PLATFORM VISION: UNIVERSAL DATA INTELLIGENCE
================================================================================

The fundamental value proposition of Dash AI is not "ThingsBoard analytics".
It is: "Give us any structured time-series or tabular data, and we will
automatically generate the best possible dashboard for it."

ThingsBoard is Phase 1. The architecture was explicitly designed so that
adding a new data source requires only:
  1. Writing a new data_fetcher variant (implementing the same raw_data
     output format)
  2. Optionally extending the Connect UI (Screen 1) to collect the
     relevant credentials or file selection
  3. No changes to DataCleaner, VizRecommender, DashboardBuilder, or
     the frontend rendering engine

The raw_data contract that Agent 1 must produce is:
  {
    "device_id":      str or identifier,
    "device_name":    str (display name),
    "device_type":    str (optional category),
    "time_range":     str (range key),
    "time_range_label": str (human label),
    "start_ts":       int (Unix ms),
    "end_ts":         int (Unix ms),
    "telemetry_keys": [str],         # ordered list of variable names
    "attribute_keys": [str],         # metadata field names
    "telemetry": {
        "key_name": [{ "ts": int, "value": any }, ...]
    },
    "attributes": {
        "key_name": { "value": any, "scope": str, "lastUpdateTs": int }
    },
    "fetched_at": str (ISO 8601)
  }

Any data source that can produce this structure — regardless of where the
data comes from — will work with the full Dash AI pipeline instantly.


4.1  DATA SOURCE ABSTRACTION LAYER
-------------------------------------------------------

The abstraction layer is the raw_data dictionary contract above. All four
agents communicate exclusively through the AgentState TypedDict. No agent
below Agent 1 ever knows or cares where the data came from.

This mirrors the Adapter design pattern: each data source is an adapter that
translates its native format into the universal raw_data schema.

Planned adapters:
  [Phase 1] ThingsBoard REST API       ← CURRENT (IMPLEMENTED)
  [Phase 2] Local file upload (CSV, Excel, JSON, Parquet)
  [Phase 3] InfluxDB / TimescaleDB (direct query)
  [Phase 3] AWS IoT Core / SiteWise
  [Phase 3] Azure IoT Hub
  [Phase 3] Google Cloud IoT Core
  [Phase 4] MQTT broker (Mosquitto, HiveMQ, EMQX)
  [Phase 4] OPC-UA (industrial protocol)
  [Phase 4] Grafana data source proxy
  [Phase 4] Third-party REST APIs (user-defined URL + key mapping)
  [Phase 5] SQL databases (PostgreSQL, MySQL, SQL Server)
  [Phase 5] Splunk, DataDog, New Relic


4.2  PHASE 2: LOCAL FILE UPLOAD MODE
-------------------------------------------------------

The most immediately impactful extension after ThingsBoard is allowing users
to simply upload a file from their local computer.

Supported formats planned:
  CSV / TSV: Each column = one sensor/variable. One column must be a timestamp.
             The file is parsed with Python's csv module or pandas.
             Column type detection reuses DataCleaner's _classify() function.
  Excel (.xlsx, .xls): Parsed with openpyxl or xlrd. Each sheet can be
             a separate "device" in multi-device mode.
  JSON: A flat list of records { "timestamp": ..., "sensor": value } or
        a dict of lists { "sensor": [{ "ts": ..., "value": ... }] }.
  Parquet: Analytical format common in data engineering pipelines.
  SQLite (.db): The user uploads a database file; the system discovers
             tables and lets the user choose which to analyse.

UI changes required:
  Screen 1 "Connect" would add a third mode tab:
    "ThingsBoard" | "Cloud API" | "Upload File"
  In Upload File mode, a drag-and-drop zone replaces the server URL inputs.
  The selected file is POSTed to a new /api/upload endpoint.

Backend:
  A new agent_file_fetcher.py adapter reads the file, detects the timestamp
  column automatically (ISO 8601, Unix epoch, Excel serial date), and
  constructs the raw_data dict. Column name heuristics (same _unit() function
  from DataCleaner) auto-assign units.

This mode requires no external server. The entire pipeline runs locally.
This makes Dash AI useful for data scientists, students, and researchers who
have no IoT platform but have exported data as CSVs.


4.3  PHASE 3: MULTI-PLATFORM CLOUD API INTEGRATION
-------------------------------------------------------

The second major expansion connects Dash AI directly to other cloud IoT and
time-series data platforms.

AWS IoT SiteWise:
  - Authenticate via AWS credentials (access key + secret or IAM role)
  - Use boto3 (AWS SDK) to list assets and asset properties
  - Fetch time-series data via get_asset_property_value_history()
  - Adapter translates AssetProperty → telemetry key, TimeSeries entry → {ts, value}

Azure IoT Hub:
  - Authenticate via connection string or EntraID (OAuth2)
  - Use azure-iot-hub SDK to list devices and query Digital Twin properties
  - Fetch telemetry from Azure Time Series Insights or Azure Data Explorer

Google Cloud IoT Core / Pub/Sub:
  - Authenticate via service account JSON
  - Fetch historical data from Cloud Bigtable or BigQuery tables
  - Map project/registry/device hierarchy to Dash AI's device model

InfluxDB (v2/v3):
  - Connect via InfluxDB client library (influxdb-client-python)
  - Execute Flux queries to retrieve measurements and fields
  - Each InfluxDB "measurement" = device_name, each "field" = telemetry key
  - Supports both cloud (InfluxDB Cloud) and self-hosted instances

TimescaleDB:
  - Connect via psycopg2 (already in requirements)
  - User provides connection string + table name + timestamp column
  - SQL SELECT with time-range WHERE clause builds the raw dataset

The UI for these sources would provide platform-specific credential forms,
with documentation links and tooltips explaining where to find each value.


4.4  PHASE 4: THIRD-PARTY & INDIRECT DATA SOURCES
-------------------------------------------------------

Beyond direct API integrations, Dash AI is designed to support indirect
data access via:

Generic REST API mode:
  The user specifies:
    - Base URL
    - Authentication header format (Bearer token, API key, Basic)
    - The JSON path to the data array (e.g. "data.readings")
    - The timestamp field name and the value field names
  Dash AI constructs the HTTP request, fetches data, and applies a JSONPath
  extractor to build the raw_data dict. This enables connecting to any
  REST-based IoT or monitoring system without writing a custom adapter.

Webhook / Push mode:
  Instead of Dash AI pulling data, external systems push data to a
  Dash AI webhook endpoint (/api/ingest/{device_token}). Incoming payloads
  are buffered and immediately available for dashboard generation.

MQTT subscriber:
  Dash AI connects to an MQTT broker (user provides host, port, topic pattern,
  TLS cert if needed), listens for a configurable time window, and collects
  all messages as the dataset. This is ideal for IoT installations that don't
  use a full platform like ThingsBoard, preferring raw MQTT.

File sync from cloud storage:
  The user provides credentials to AWS S3, Azure Blob Storage, or Google
  Cloud Storage. Dash AI downloads the latest CSV/Parquet export from the
  bucket and processes it as a local file. This is common in industrial IoT
  where historians export data on a schedule to object storage.


4.5  PHASE 5: ENTERPRISE & INDUSTRIAL DATA SOURCES
-------------------------------------------------------

For large-scale enterprise deployments:

OPC-UA:
  The OPC Unified Architecture is the dominant protocol in industrial
  automation (SCADA, PLC, DCS systems). A Dash AI OPC-UA adapter using the
  opcua-asyncio or asyncua library can browse node trees, read historical
  values via HDA (Historical Data Access), and feed them into the pipeline.
  This enables Dash AI to create dashboards directly from Siemens, ABB,
  Rockwell, and Honeywell industrial systems.

SQL databases (general):
  The user provides a connection string (SQLAlchemy DSN) and either writes a
  simple SELECT query or uses a visual column-picker UI. The result set is
  treated as tabular telemetry data. This enables Dash AI to work with any
  well-structured relational database that stores time-series measurements.

DataDog / New Relic / Splunk:
  These are observability platforms used in IT/DevOps. Dash AI could fetch
  metric time-series (CPU, memory, request latency, error rates) via their
  respective APIs and render them as dashboards, effectively becoming a
  zero-config observability dashboard layer on top of existing monitoring stacks.

Data marketplace APIs:
  Public datasets (weather, financial markets, environmental sensors, satellite
  readings) available via standard REST APIs can be ingested through the
  generic REST mode, allowing Dash AI to serve research and public data
  visualisation use cases.

In all cases above, the output is identical: a Dash AI personalized dashboard
rendered in the browser, saveable, shareable, and conversationally queryable
via the AI chat widget. The user never needs to know or care what system
provided the underlying data.

5. LITERATURE SURVEY

This section surveys key academic and industry work relevant to the core
capabilities of Dash AI: IoT data management, automated visualisation,

5.1  IoT DATA MANAGEMENT & PLATFORMS
-------------------------------------------------------

The Internet of Things (IoT) has grown to encompass an estimated 15+ billion
connected devices globally as of 2024 (Statista, 2024), generating unprecedented
volumes of time-series telemetry data. Managing, storing, querying, and
visualising this data has become a central challenge in computer science and
systems engineering.

Botta et al. (2016) classified IoT Cloud platforms along dimensions of service
model (IaaS, PaaS, SaaS), data model, and API design, noting that the lack of
interoperability between platforms was a key obstacle to IoT adoption. This
observation directly motivates Dash AI's data-source-agnostic design: by
presenting a unified interface over heterogeneous backends, the platform
resolves the interoperability problem at the analytics layer.

ThingsBoard specifically implements the Actor Model (Lightbend Akka) for
device message processing and uses Cassandra or PostgreSQL for time-series
storage, providing sub-second write latency at scale (ThingsBoard Technical
Documentation, 2023). Dash AI connects to ThingsBoard's REST API, which
exposes this data in a universally accessible JSON format.

AWS IoT SiteWise (2021) and Azure IoT Hub (2017) represent the cloud-native
enterprise IoT management tier, providing proprietary data models and APIs
that become accessible via Dash AI's Phase 3 adapters. Ngu et al. (2017)
provide a comprehensive structured survey of IoT middleware platforms,
confirming the diversity of API paradigms and reinforcing the need for
an abstraction layer such as Dash AI's DataFetcher interface.


5.2  AI/ML FOR AUTOMATED DATA VISUALISATION
-------------------------------------------------------

Automated visualisation generation has been studied in the data visualisation
community for over two decades. Mackinlay (1986) introduced APT (A Presentation
Tool), which formalised the selection of graphical encodings based on data
types and perceptual effectiveness principles. This foundational work
established that the best chart type for a dataset can, in principle, be
determined algorithmically.

Wongsuphasawat et al. (2016) presented Voyager, a system that recommends
visualisations by scoring combinations of fields and chart types using a
formal perceptual effectiveness model. Voyager's graphical mark selection
logic (point for scatter, line for time, bar for categorical) is echoed in
Dash AI's VizRecommender agent's fallback mode and in the constraints encoded
in the Groq system prompt.

The VizML project (Hu et al., 2019) collected 31 million real-world plotly
charts and trained a classifier to predict chart types from dataset features
(cardinality, monotonicity, data type). Dash AI takes a related but different
approach: it delegates this prediction to a large language model that has
been trained on vast corpora including data science literature, documentation,
and chart-data pairs, enabling zero-shot generalisation to new sensor types
without any training data.

NL4DV (Narechania et al., 2021) introduced a natural language interface for
generating Vega-Lite visualisations from text queries. Dash AI's conversational
chat widget (Section 8.9) extends this concept beyond chart generation to
natural language Q&A over the data, using the dashboard's pre-computed
statistics as grounding context.


5.3  LARGE LANGUAGE MODELS IN ANALYTICS
-------------------------------------------------------

The application of large language models (LLMs) to structured data analysis
is a rapidly evolving field. OpenAI's GPT-4 (OpenAI, 2023) demonstrated that
transformer models can reason over tabular data, write SQL queries, generate
Python data analysis code, and interpret descriptive statistics.

Cheng et al. (2023) introduced "Is Your LLM Secretly a World Model?" which
showed that LLMs encode implicit knowledge about sensor physics, domain norms,
and causal relationships — making them particularly suited to IoT analytics
where sensor context (a "temperature" sensor should be between -40°C and
150°C; a "battery" should be between 0% and 100%) improves interpretation
quality significantly.

Dash AI exploits this implicit world knowledge in two places:
  1. VizRecommender: The Groq system prompt instructs the LLM to select chart
     types based on sensor semantics, not just data types. The model knows that
     CO2 concentration benefits from a trend line, that boolean on/off status
     is best shown as a doughnut, and that correlated sensors may be best
     compared in a scatter plot.
  2. Chat widget: The llama-3.1-8b-instant model is grounded with precise
     statistics (mean, min, max with timestamps, trend, anomaly count) and can
     answer natural language questions like "when was the peak temperature?" or
     "is the humidity trending towards dangerous levels?" accurately.

Ma et al. (2023) proposed "Large Language Models as Tool Makers", demonstrating
that LLMs can produce executable code that processes structured data. Dash AI's
DashboardBuilder agent takes a complementary approach, generating Chart.js
configuration objects (JSON) rather than Python code, which the browser executes
directly. This sidesteps the sandboxing concerns of LLM-generated code while
achieving the same personalisation effect.

The choice of Groq as the inference provider (rather than OpenAI or Anthropic)
is driven by Groq's industry-leading inference speed: up to 500 tokens/second
on LPU hardware (Groq, 2024), making the sub-second latency VizRecommender
response a realistic product experience rather than a research prototype.


5.4  DASHBOARD GENERATION & NLP-TO-CHART SYSTEMS
-------------------------------------------------------

Several systems have explored the pipeline from raw data to dashboard, each
with different assumptions and trade-offs:

  Grafana (Grafana Labs, 2014–present):
    The dominant open-source monitoring dashboard platform. Grafana requires
    users to manually configure every panel: select data source, write query,
    choose chart type, set axes. Dash AI's value proposition is the elimination
    of this manual configuration step.

  Kibana (Elastic, 2013–present):
    Elasticsearch's visualisation layer, offering auto-suggest for field names
    but still requiring manual chart assembly. While Elastic Lens (introduced
    2020) automates some chart recommendations, it is bound to Elasticsearch
    as a data source.

  Google Looker Studio (formerly Data Studio):
    Provides template-based dashboards and some chart suggestions, but still
    requires the user to select fields and chart types. No AI pipeline.

  Chat2DB (GitHub, 2023):
    An LLM-powered SQL query assistant that generates SQL from natural language
    and renders results as charts. Similar in spirit to Dash AI's chat widget
    but focused on relational databases rather than time-series telemetry.

  AutoViz (Bokeh-based, 2020):
    A Python library that automatically generates visualisations for a DataFrame.
    It uses rule-based heuristics (data type + cardinality) to select chart
    types. Dash AI's VizRecommender goes beyond rules to use LLM reasoning,
    enabling context-aware and domain-adaptive chart selection.

Dash AI's distinctive contribution to this space is the combination of:
  (a) Multi-source data ingestion with a unified adapter interface
  (b) Statistical analysis with explicit anomaly flagging and trend detection
  (c) LLM-driven chart selection with graceful rule-based fallback
  (d) Real-time streaming overlaid on a statically-generated dashboard
  (e) Conversational AI grounded in precise dashboard statistics
  (f) One-click save, share, and PDF export


5.5  ANOMALY DETECTION IN TIME-SERIES DATA
-------------------------------------------------------

Anomaly detection in IoT sensor streams is a well-studied problem. The
taxonomy of anomaly types includes point anomalies (individual outliers),
contextual anomalies (normal value, abnormal context), and collective anomalies
(sequences that deviate from the norm).

Chandola et al. (2009) provided a comprehensive survey of anomaly detection
techniques, categorising them into statistical, proximity-based, information-
theoretic, and spectral methods. Dash AI implements the simplest effective
approach from this taxonomy: the z-score method (standard deviation threshold).

A value v is flagged as anomalous if |v - μ| > 2.5σ, where μ is the mean
and σ the standard deviation of the sensor time series. This threshold of 2.5σ
corresponds to flagging values in the top/bottom ~1.2% of a Gaussian distribution
— empirically a good balance between sensitivity and false-positive rate for IoT
sensor data. The flagged points are rendered as red circles in Chart.js plots.

More sophisticated methods — LSTM-based anomaly detection (Malhotra et al.,
2015), Isolation Forest (Liu et al., 2008), or STL decomposition (Cleveland
et al., 1990) — are natural future improvements, particularly for seasonal
patterns (e.g., daily temperature cycles) where simple z-scores generate
excessive false positives.

The pattern detection logic in DataCleaner also identifies:
  - Constant series (zero variance): indicates a stuck sensor or offline device
  - Monotonic trends (linear regression slope): rising/falling sensor readings
  - Boolean extremes (always ON or always OFF for the period): unusual device state
  - Categorical mode concentration (≤8 unique string values): state-machine view


5.6  REAL-TIME DATA STREAMING
-------------------------------------------------------

Real-time data delivery to browser clients is implemented via WebSockets —
a full-duplex communication protocol over a single TCP connection, standardised
by RFC 6455 (IETF, 2011). The Flask-SocketIO library (Grinberg, 2014–present)
provides a Pythonic abstraction over the Socket.IO protocol, which adds
namespace management, room-based broadcasting, automatic reconnection, and
graceful HTTP long-poll fallback for environments where WebSockets are blocked.

Earlier approaches to real-time browser updates include:
  Server-Sent Events (SSE): One-directional HTTP stream. Simpler but cannot
    handle bidirectional communication (needed for chat widget and subscribe/
    unsubscribe control messages).
  HTTP Long Polling: Client repeatedly polls with a timeout. High latency and
    server resource overhead.
  WebSockets: Lowest latency, lowest overhead, bidirectional. Standard choice
    for IoT dashboards since 2014.

Dash AI's streaming architecture is a hybrid:
  - Historical data: fetched synchronously at dashboard generation time via REST
  - Live updates: delivered asynchronously via Socket.IO every 3 seconds
  - Update throttling: the browser maintains a 20-point rolling window per chart

This hybrid approach provides the best of both worlds: a rich historical view
from the AI pipeline, continuously augmented by live data without full
re-generation of the dashboard or AI calls.

The APScheduler background job that drives the live feed was fixed in this
build to guard against the Werkzeug debug reloader double-start problem
(see Section 12, Known Issue #2).

8.3  PIPELINE ORCHESTRATOR — pipeline.py (47 lines)
-------------------------------------------------------

Defines AgentState (Python TypedDict) — the shared data contract between agents:

  session_id, tb_host, tb_token, device_id, device_name, time_range
  raw_data, cleaned_data, patterns, viz_recommendations, dashboard_data
  errors, warnings, agent_statuses

run_pipeline():
  1. Generates session ID: MD5(token + device_id + current_time)[:12]
  2. Persists session to DB
  3. Initialises all agent statuses to "pending"
  4. Calls: DataFetcher → DataCleaner → VizRecommender → DashboardBuilder
  5. Returns complete AgentState

Error propagation: each agent checks the previous agent's status before
running. If the preceding agent errored, the current agent sets its own
status to "skipped" and returns immediately. This prevents wasted computation
on downstream agents when upstream data is unavailable.


8.4  AGENT 1: DATA FETCHER — agents/data_fetcher.py (141 lines)
-------------------------------------------------------

The only Phase-1-specific agent. Its entire logic is ThingsBoard REST calls.

Flow per device:
  1. Resolve device name and type from /api/device/{id}
  2. List available telemetry keys from /keys/timeseries
  3. List attribute keys from /keys/attributes
  4. Batch-fetch time-series for up to 20 keys (1000 points each, 60s timeout)
  5. Fetch attributes from client + server + shared scopes
  6. Combine into raw_data dict with optional device-name prefix for multi-device

Error handling: HTTP 401 (token expired) → fatal & return. HTTP 404 (device
not found) → log warning, skip that device. Timeout or ConnectionError → fatal.

Contract output: raw_data dict (see Section 4.1 for full schema)

FUTURE EXTENSION POINT: A new data source requires a new file in agents/,
implementing the same function signature:
  def agent_X_fetcher(state: AgentState) -> AgentState:
  The function must populate state["raw_data"] with the universal schema.


8.5  AGENT 2: DATA CLEANER — agents/data_cleaner.py (240 lines)
-------------------------------------------------------

Universal statistical analysis. Entirely data-source-agnostic.

Type classification (_classify):
  null, boolean (bool type or true/false/yes/no/on/off/0/1 strings),
  numeric (float-parseable), json (dict-like string), string (everything else)

Numeric analysis per key:
  - Statistics: count, mean, min, max, variance, standard deviation
  - Trend: linear regression slope → rising (>1%/step) / falling / stable
  - Anomaly detection: z-score threshold 2.5σ → point anomaly flags
  - Output slice: last 300 values + anomaly_flags boolean list

Pattern generation:
  trend     → rising/falling sensor identified with direction
  anomaly   → count + timestamps of last 3 anomalous readings
  constant  → std=0, sensor is stuck or reporting same value
  status    → boolean always-ON or always-OFF
  categorical → string sensor with ≤8 unique values lists all states

JSON nested extraction:
  Sensor values that are JSON objects (common in gateway devices that pack
  multiple readings into one key) are automatically flattened:
  "gps" → "gps.lat", "gps.lng" each become separate numeric timeseries.

Unit heuristics (_unit):
  16 keyword patterns detect physical units from key names:
  temperature→°C, humidity→%, pressure→hPa, voltage→V, current→A,
  power→W, energy→kWh, speed→m/s, CO2→ppm, particles→µg/m³,
  signal→dBm, battery→%, frequency→Hz, light→lux, flow→L/min,
  level→cm, pH→pH

Optional AI pass (Groq llama-3.1-8b-instant):
  If ≥2 numeric sensors and Groq is available, asks for cross-sensor
  correlations in JSON format. Parsed with regex r'\[[\s\S]*\]' and
  appended to patterns list. Silently ignored on failure.


8.6  AGENT 3: VIZ RECOMMENDER — agents/viz_recommender.py (112 lines)
-------------------------------------------------------

Selects optimal chart types using Groq Mixtral-8x7b-32768 (LLM) or deterministic
fallback. Produces a list of 6-12 chart specifications.

Supported chart types (14):
  line, bar, doughnut, pie, area, stacked_bar, combo, bubble, scatter,
  radar, polarArea, kpi, boolean_status, string_freq

Groq system prompt encodes rules for each chart type:
  - line: time-series numeric trends, anomaly tracking
  - bar: comparing averages across sensors
  - doughnut/pie: on/off ratios, categorical proportions
  - area: volume/cumulative metrics
  - stacked_bar: parts-of-whole across sensors
  - combo: mixed line+bar for 2 correlated sensors
  - bubble: 3 sensors as (x, y, radius)
  - scatter: 2 correlated sensors
  - radar/polarArea: 3-6 sensors as multi-dimensional profile
  - kpi: single most critical numeric reading
  - boolean_status: on/off with percentage bar
  - string_freq: horizontal bar of value frequencies

User prompt includes all sensor statistics + patterns + device context.
Response must be raw JSON array only. Regex fallback extracts array if extra
text is present. Invalid chart types are filtered out.

Fallback (_fallback_viz):
  Deterministic rule-based selection when Groq is unavailable:
  - Line chart per numeric sensor (up to 4)
  - Radar if ≥3 numeric sensors
  - Bar of averages if ≥2 numeric sensors
  - Boolean_status per boolean sensor (up to 3)
  - String_freq for first string sensor
  - KPI for first numeric sensor
  Never fails. Always produces a usable dashboard.


8.7  AGENT 4: DASHBOARD BUILDER — agents/dashboard_builder.py (252 lines)
-------------------------------------------------------

Translates all pipeline outputs into a final JSON structure renderable by the
browser without any further processing.

KPI cards (up to 8):
  Each numeric sensor → { key, label, avg, min, max, std, trend,
                          anomaly_count, count, unit, min_ts, max_ts, raw_data }
  raw_data = last 60 (timestamp, value) pairs for the detail modal.
  min_ts/max_ts = exact timestamps of extreme values for AI chat precision.

Boolean cards:
  Each boolean sensor → { key, label, true_count, false_count,
                          true_pct, last_value, count }

String cards:
  Each string sensor → { key, label, latest, top-6 by frequency,
                          total, unique counts }

Chart blocks (_build_chartjs):
  Line/Area/Bar/Stacked/Combo/Scatter:
    Up to 4 datasets per chart. Timestamps as "DD/MM HH:MM" labels.
    Anomalous points rendered in red (#ef4444) with +4px radius.
    For >80 points, base point radius = 0 (performance).
    Color palette: #3b82f6, #ef4444, #10b981, #f59e0b, #8b5cf6,
                   #14b8a6, #f43f5e, #6366f1
  Doughnut/Pie: boolean (green/gray) or top-6 string values (multi-color)
  Radar/PolarArea: ≥3 sensors normalised to 0-100% scale
  Bubble: exactly 3 sensors as (x, y, radius), radius scaled 5-20px

Attribute table:
  All device attributes with pretty label, value (truncated to 200 chars),
  scope tag (client/server/shared/device), and type classification.

         → DB UPSERT dashboard → response: { share_token }
Step 13: User clicks Share → copies /share/{token} to clipboard
Step 14: Recipient visits /share/{token}
         → GET /share/{token}: render dashboard.html with metadata only
         → DOMContentLoaded: GET /api/shared/{token} (full JSON)
         → renderDashboard() in read-only mode (no save/share/export buttons)

10. SECURITY ARCHITECTURE
================================================================================

User authentication:
  Flask session (server-side cookie). Werkzeug password hashing
  (pbkdf2:sha256 or scrypt). @login_required decorator gates all
  authenticated endpoints.

ThingsBoard token handling:
  JWT stored only in browser JavaScript (S.token). Never written to the
  Dash AI database. Forwarded to ThingsBoard only in the X-Authorization
  header of API calls. In-memory only in active_sessions for WebSocket
  polling; purged on disconnect.

Data storage:
  Device telemetry is NOT stored in the Dash AI database. The dashboard_data
  JSON (aggregated statistics + chart configs) is stored only when the user
  explicitly saves a dashboard. Raw sensor values are never persisted.

XSS prevention:
  All user-supplied strings rendered in template literals or innerHTML pass
  through esc(s): &→&amp; <→&lt; >→&gt; "→&quot;

Share token security:
  secrets.token_urlsafe(16) ≈ 128 bits of entropy. Impossible to enumerate.
  No expiry or revocation mechanism currently (see Known Issues).

SSL:
  HTTPS used for all Groq API calls (enforced by requests).
  ThingsBoard calls: verify=True by default, falls back to verify=False
  on SSLError for self-signed certs (usability trade-off).

CSRF:
  No CSRF token implementation. All state-modifying endpoints are JSON POST,
  which provides partial protection (browsers enforce same-origin for
  non-CORS fetches). Full CSRF protection is a planned improvement.

Session secret:
  FLASK_SECRET from .env or Render env var. If missing, os.urandom(24).hex()
  is generated per-process (sessions lost on restart). Production deployments
  should always set an explicit secret.

11. DEPLOYMENT ARCHITECTURE
================================================================================

Development:
  python app.py → Flask-SocketIO dev server on port 5050, debug=True
  SQLite (dashboard.db) for local database
  .env file for secrets

Production (Render.com):
  gunicorn app:app (single WSGI worker)
  PostgreSQL via Neon serverless (DATABASE_URL env var)
  FLASK_SECRET generated by Render (stable across deploys)
  GROQ_API_KEY set manually in Render dashboard
  PYTHON_VERSION = 3.11.0

render.yaml:
  type: web, name: dash-ai, env: python
  buildCommand: pip install -r requirements.txt
  startCommand: gunicorn app:app

Known production issue: bare gunicorn does not support WebSockets.
For live telemetry to work in production, the start command must be:
  gunicorn --worker-class eventlet -w 1 app:app
and eventlet must be added to requirements.txt.

Alternatively, Render supports a "Background Worker" service type, which
could host the APScheduler loop as a separate process, decoupling it from
the web server lifecycle and improving reliability.


================================================================================
12. KNOWN ISSUES & LIMITATIONS
================================================================================

Issue 1: Sidebar logout button broken
  The "→ Sign Out" button in the dashboard sidebar calls onclick="logout()"
  but no logout() JavaScript function is defined in the script block.
  The browser will throw ReferenceError. The topbar sign-out link (<a href="/logout">)
  defined in base.html works correctly.
  Fix: Change to onclick="window.location.href='/logout'"

Issue 2: APScheduler double-start in debug mode (RESOLVED)
  Previously scheduler.start() ran at module import time. Werkzeug's debug
  reloader forks the process; the scheduler started in both parent and child,
  causing doubled background threads that blocked the response queue during
  logout (producing noticeable delay).
  Fix applied: guarded with os.environ.get('WERKZEUG_RUN_MAIN') != 'false'

Issue 3: Polling timeout reduced to 2s (APPLIED)
  ThingsBoard telemetry poll timeout reduced from 5s to 2s to reduce the
  maximum blocking time of background threads on the response queue.

Issue 4: Gunicorn + WebSocket incompatibility (PRODUCTION)
  render.yaml uses bare gunicorn app:app. Socket.IO WebSocket support requires
  an event-loop-based worker class (eventlet or gevent). Without this, WebSocket
  connections fall back to HTTP long polling or fail entirely in production.

Issue 5: No CSRF protection
  State-changing endpoints (/api/dashboards POST/DELETE, /run) have no CSRF
  tokens. Risk is partially mitigated by JSON content-type requirements.

Issue 6: Synchronous pipeline
  POST /run blocks the Flask worker for up to 30+ seconds on slow ThingsBoard
  instances or complex datasets. Under high concurrency, this exhausts workers.
  Production fix: background task queue (Celery/RQ) with SSE progress stream.

Issue 7: Telemetry key limit
  Only 20 telemetry keys fetched per device (API batch call). Devices with
  more sensors will have some silently ignored. A paginated multi-request
  approach would resolve this.

Issue 8: No share link expiry or revocation
  Share tokens are permanent unless the dashboard is deleted. No per-link
  access control, view count, or time-to-live mechanism.

Issue 9: Database connection pooling absent
  Each DB operation opens and closes a new connection. Adequate for low traffic,
  but a connection pool is required for production scale.

Issue 10: FLASK_SECRET regenerated on restart
  If FLASK_SECRET is absent from the .env file, os.urandom generates a new
  secret each restart, invalidating all existing user sessions.

Issue 11: Chat context overflow
  For dashboards with many sensors or large pattern lists, the /api/chat
  payload may approach Groq's context window limit, potentially truncating
  important statistics.
